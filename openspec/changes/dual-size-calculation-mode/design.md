## Context

当前 `scanner.rs` 使用 `metadata.len()` 计算文件大小，这只返回文件的逻辑大小（实际内容字节数）。macOS 的 `du -sh` 命令使用 `st_blocks * 512` 计算磁盘使用量，包含文件系统块分配开销。两者在小文件、稀疏文件、压缩文件等场景下差异显著。

现有架构：
- 后端：Rust + walkdir 扫描，返回 `FileInfo` 列表
- 前端：React + TypeScript，接收并显示扫描结果
- 数据流：扫描 → 序列化 → 事件发送 → 前端渲染

## Goals / Non-Goals

**Goals:**
- 扫描时同时计算逻辑大小和磁盘使用量
- 前端提供切换控件，用户可选择显示哪种尺寸
- 最小大小过滤支持按选定模式进行
- 向后兼容，不破坏现有 API 接口

**Non-Goals:**
- 不修改现有的扫描算法核心逻辑
- 不引入新的外部依赖（使用标准库的 `MetadataExt`）
- 不改变现有的文件大小单位换算逻辑（前端 `formatFileSize` 保持不变）

## Decisions

### 1. 双字段方案 vs 单字段切换方案
**决策：** 采用双字段方案，`FileInfo` 同时包含 `size`（逻辑大小）和 `disk_usage`（磁盘使用量）

**理由：**
- 一次扫描即可获得两种尺寸，避免重复计算
- 前端切换模式时无需重新扫描
- 未来可扩展支持更多计算模式（如包含元数据开销等）

### 2. 磁盘使用量计算方式
**决策：** 使用 `metadata.blocks() * 512`（POSIX 标准块大小）

**理由：**
- 与 macOS `du` 命令的计算方式一致
- `blocks()` 在 `std::os::unix::fs::MetadataExt` 中提供，无需外部依赖
- 512 字节是 POSIX 标准块大小，跨平台兼容性好

### 3. 前端状态管理
**决策：** 在 `App.tsx` 中添加 `sizeMode` 状态，通过 props 传递给子组件

**理由：**
- 应用规模较小，无需引入全局状态管理库
- 保持现有的组件通信模式一致
- 切换模式时只需更新显示逻辑，无需重新获取数据

### 4. 最小大小过滤
**决策：** 保持现有的 `min_size` 过滤逻辑，基于逻辑大小进行过滤

**理由：**
- 避免在扫描阶段引入复杂的模式判断
- 逻辑大小过滤已能满足大多数用户需求
- 如需支持按磁盘使用量过滤，可在后续迭代中添加

## Risks / Trade-offs

### [Risk] blocks() 在某些文件系统上可能返回 0
**Mitigation:** 添加容错处理，如果 `blocks() == 0`，则回退到使用 `len()` 作为磁盘使用量的近似值

### [Risk] 增加字段会略微增加序列化开销
**Mitigation:** 每个 FileInfo 仅增加一个 u64 字段，影响可忽略不计

### [Risk] 前端切换模式时，排序可能需要重新计算
**Mitigation:** 当前按大小排序是在后端完成的，前端切换模式后可能需要重新排序。暂时保持后端排序，后续可考虑前端排序优化

### [Trade-off] 扫描时间略微增加
**Mitigation:** `blocks()` 和 `len()` 都来自同一 `metadata` 调用，额外开销极小
